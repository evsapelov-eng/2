# Архитектура и технические риски

Документ фиксирует результаты этапа 1 «Проверка архитектуры».

> Во время разработки официальная документация Telegram, Google AI и GitHub была
> недоступна из среды сборки (сетевые ограничения). Поведение SDK `google-genai`
> проверено на установленной версии 3.6.1, остальное — по знанию API. Пункты,
> отмеченные **«проверить»**, владелец должен сверить с актуальными страницами
> перед запуском. Ссылки приведены в конце.

## Схема

```
Группа обсуждений PLUIT Club
        │  (бот — обычный участник, Privacy Mode выключен)
        ▼
GitHub Actions (cron 5 раз в день + ручной запуск)
        │
        ├─ загрузка состояния: ветка bot-state → AES-256-GCM → SQLite в памяти
        ├─ getUpdates пакетами по 100 (offset подтверждается только после сохранения)
        ├─ сохранение постов и комментариев, привязка к постам, ответы автора
        ├─ анализ: фильтр реакций → Gemini (пакетами) → правила при недоступности AI
        ├─ приоритеты, входящие, идеи
        ├─ команды и кнопки владельца
        ├─ очередь уведомлений (outbox) → личный чат владельца
        └─ сохранение состояния: новый orphan-коммит в bot-state (force-with-lease)
```

Один запуск — один короткий процесс. Между запусками ничего не работает и минуты
Actions не расходуются. Исключение — «окно быстрых ответов» (по умолчанию 90 секунд),
которое открывается только если владелец в этом запуске пользовался ботом.

## Ключевые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Получение сообщений | `getUpdates`, без webhook | Не нужен сервер. При запуске webhook проверяется и отключается без `drop_pending_updates`. |
| Видимость комментариев | Privacy Mode выключен, бот — обычный участник группы | Не нужны права администратора. Альтернатива — администратор без единого права. |
| Пост ↔ комментарий | `is_automatic_forward` + `forward_origin` (тип `channel`) дают пару «ID поста в канале ↔ ID пересылки в группе»; комментарии связываются по `message_thread_id`, `reply_to_message` и родителю | ID в канале и группе не совпадают. Если пост неизвестен — 3 повторные попытки, затем анализ без привязки. |
| HTTP-клиент | `httpx` (async) вместо aiogram | Нужны 10 методов Bot API, диспетчер aiogram и long polling не используются. |
| AI | Официальный SDK `google-genai`, `response_schema` (Pydantic) | Структурированный JSON + повторная валидация Pydantic. |
| Экономия квоты | До 8 комментариев одного поста в одном запросе | Бесплатный лимит — порядка 20 запросов в сутки на модель (**проверить**). |
| Хранилище | SQLite → zlib → AES-256-GCM → ветка `bot-state` | Ниже — сравнение альтернатив. |
| Параллельные запуски | `concurrency` в workflow + `--force-with-lease` при сохранении | Второй уровень защиты: устаревшая копия не перезапишет новую. |
| Дубли уведомлений | Очередь `outbox` с уникальным ключом, статус `sending` сохраняется до отправки | Если запуск оборвался во время отправки, сообщение не отправляется повторно. |

## Надёжность получения обновлений

1. `getUpdates(offset=N)` подтверждает Telegram все обновления с `update_id < N`.
2. Бот вызывает `getUpdates` с новым offset только после того, как предыдущий пакет
   сохранён в ветку `bot-state`. Пакет из 100 — промежуточное сохранение и следующий
   запрос; неполный пакет подтверждается следующим запуском.
3. Сырые обновления хранятся в таблице `raw_updates` до обработки; сообщения
   уникальны по `(chat_id, message_id)`, повтор обновления не создаёт дубль.
4. Если сохранение не удалось — запуск завершается ошибкой, offset в Telegram не
   продвинут, следующий запуск получит те же обновления.

## Хранилище состояния: сравнение

| Вариант | Бесплатно | Минусы |
|---|---|---|
| **Ветка `bot-state` (выбрано)** | Да, без новых аккаунтов | Размер ограничен разумными десятками МБ; удаление из истории зависит от сборки мусора GitHub. Решено orphan-коммитами: в ветке всегда один коммит. |
| GitHub Actions Cache | Да | Кэш удаляется через 7 дней без обращений и при превышении 10 ГБ — нельзя быть единственным хранилищем (так и указано в ТЗ). |
| Артефакты Actions | Да | Срок хранения до 90 дней, для чтения нужен API-вызов к прошлому запуску; при сбое цепочки состояние теряется. |
| Gist | Да | Нужен отдельный персональный токен (лишний секрет с широкими правами), история ревизий копится. |
| Supabase / Neon (Postgres) | Бесплатный тариф | Отдельный аккаунт; у Supabase бесплатный проект приостанавливается после недели без активности (**проверить**). |
| Turso (SQLite в облаке) | Бесплатный тариф | Отдельный аккаунт и токен; надёжный вариант, если ветка станет неудобна. |
| Cloudflare R2 / D1 | Бесплатный тариф | R2 требует привязки карты (**проверить**) — противоречит требованию. |

Вывод: ветка репозитория — самый надёжный вариант без дополнительных аккаунтов и карт.
Если владелец захочет хранить данные вне GitHub, разумная альтернатива — Turso; её
можно подключить, реализовав ещё один `StateBackend` (интерфейс `fetch/store`).

## Технические риски и ограничения

1. **Регион Gemini API.** По последним известным данным, Россия не входит в список
   регионов, где доступен Gemini API (**проверить**: страница available-regions).
   Запросы идут с серверов GitHub (США) и технически проходят, но создание ключа в
   AI Studio и условия использования — ответственность владельца аккаунта Google.
   Без ключа бот полностью работает в режиме анализа по правилам (без вариантов ответа).
2. **Данные на бесплатном тарифе Gemini.** Условия Gemini API для бесплатных
   («Unpaid») сервисов разрешают Google использовать переданные данные для улучшения
   продуктов, в том числе с участием людей-рецензентов (**проверить** текущую
   редакцию). Поэтому в AI не передаются имена и username подписчиков, а до согласия
   владельца рекомендуется работать на тестовых данных. Подробнее — `docs/PRIVACY.md`.
3. **Квота Gemini.** Бесплатный лимит — порядка 20 запросов в сутки на модель
   (данные из соседнего проекта владельца, **проверить** в AI Studio → Rate limits).
   По умолчанию бот использует не более 18 запросов в сутки на модель и 10 за запуск,
   две бесплатные модели (`gemini-3.7-flash`, запасная `gemini-3.8-flash`). Счётчик
   ведётся по тихоокеанскому времени — по нему сбрасывается лимит. Если на проекте
   Google Cloud включён биллинг, тот же ключ станет платным: **используйте проект без
   биллинга.**
4. **24 часа в очереди Telegram.** Необработанные обновления Telegram хранит не более
   суток. Если GitHub Actions не запускался дольше (сбой, отключённые Actions),
   комментарии за этот период будут потеряны. История переписки через Bot API
   недоступна.
5. **Удаление сообщений.** Bot API не сообщает об удалении комментариев: удалённый
   подписчиком комментарий остаётся в базе до истечения срока хранения.
6. **Задержка кнопок.** Нажатия обрабатываются при следующем запуске (до 3 часов, ночью
   дольше). Telegram показывает «часики» на кнопке и снимает их сам; ответ на нажатие
   может уже не дойти — это нормально. «Открыть комментарий» — URL-кнопка, работает
   сразу. Внеплановый запуск: Actions → PLUIT Assistent → Run workflow (в том числе из
   мобильного приложения GitHub).
7. **Расписание GitHub.** Плановые запуски могут задерживаться (иногда на десятки
   минут) или пропускаться при высокой нагрузке. Расписание работает только из
   ветки по умолчанию.
8. **Минуты Actions.** Для приватных репозиториев на GitHub Free — 2000 минут в месяц
   (**проверить** Settings → Billing). Ожидаемый расход: ~155 запусков × 1–2 минуты =
   150–310 минут, плюс тесты при пушах и окна быстрых ответов.
9. **Ключ шифрования.** Потеря `STATE_ENCRYPTION_KEY` = потеря накопленных данных.
   Сохраните ключ в менеджере паролей.
10. **Ответы от имени канала/анонимно.** Ответ от имени канала (`sender_chat` = канал)
    засчитывается как ответ автора. Анонимный администратор (`sender_chat` = группа)
    — нет: нельзя достоверно определить, кто писал.
11. **Права на запись.** `GITHUB_TOKEN` получает `contents: write` — это минимум для
    сохранения состояния. Защита веток (branch protection) не должна распространяться
    на `bot-state`.
