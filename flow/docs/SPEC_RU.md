# 1. ЦЕЛЬ И ОСНОВНОЙ СЦЕНАРИЙ

FLOW — один Max for Live MIDI Effect с двумя режимами: ARRANGE для подготовки концертных секций и PERFORM для выступления. Он управляет глобальной структурой Ableton Arrangement View и опционально отправляет MIDI Program Change в Digitone II, а не генерирует или микширует звук.

Типовой концерт: пользователь готовит 45–90 минут материала в Arrangement View, включая аудиоплейбэки, VST, MIDI-дорожки, автоматизацию и заранее записанные секции для внешнего синтезатора. FLOW показывает карту выступления. На внешнем MIDI-контроллере пользователь нажимает HOLD, чтобы продлить выбранный фрагмент; RELEASE, чтобы после цикла вернуться к линейному продолжению; NEXT, чтобы перейти к другой секции; STOP — для глобальной остановки, причём безопасность STOP зависит от выбранного режима.

На Digitone II пользователь продолжает играть на инструменте и менять звучание руками. Передача аудио может происходить отдельно по аналоговым кабелям или через USB Audio/MIDI, не влияя на архитектуру FLOW.

# 2. ГРАНИЦЫ ПРОЕКТА

## Входит в MVP

1. Один M4L MIDI Effect в Ableton Live 12.
2. Компактная панель устройства и отдельный увеличиваемый редактор/окно Max.
3. Два режима: ARRANGE и PERFORM.
4. Таблица секций с именем, временем начала, длительностью, опциональным паттерном Digitone, режимом зацикливания.

7. HOLD текущей или выбранной секции через Arrangement Loop.
8. RELEASE: снятие петли и продолжение аранжировки на проверенной музыкальной границе.
9. NEXT / PREVIOUS: переходы по секциям, строго определённые для натурального и пользовательского порядка.

12. Оповещения о конфликтующих состояниях Live.
13. DEMO MODE без оборудования и диагностический журнал.
14. Воспроизводимые тестовые Live Set и сценарии приёмки.

1. Переключение Digitone II по Program Change через выделенный MIDI-маршрут; сначала тест отдельного MIDI-компонента.

- Управление устройством без запущенного Live (standalone).

# 3. ВАЖНЕЙШАЯ МОДЕЛЬ ДАННЫХ: ДВА ПОРЯДКА

В Ableton уже размещены аудиоклипы, MIDI и автоматизация. Нельзя создавать ложное ожидание, что перетаскивание секции FLOW физически перемещает этот материал.

Различать:

**SOURCE TIMELINE** — реальные фиксированные координаты исходных фрагментов в Arrangement View, в beat time.

**PERFORMANCE ORDER** — изменяемая последовательность ссылок на секции исходного Arrangement, по которой пользователь может переходить во время концерта.

Например, исходные области: INTRO [0,64), GROOVE [64,192), BREAK [192,256), DROP [256,384). Пользователь может создать PERFORM ORDER INTRO → GROOVE → BREAK → GROOVE → DROP, не двигая исходные клипы. Повтор GROOVE — ещё одна ссылка на [64,192), а не новый аудиоклип.

ARRANGE имеет два вида:
- SOURCE: секции располагаются по реальным стартовым координатам, ширина соответствует их длине. Сортировка по `startBeat`.
- SETLIST: перетаскивание меняет только `performanceOrder`. Никакие клипы Ableton не модифицируются.

Указать это прямо в интерфейсе: `SETLIST: references only — Live clips unchanged`.

Если участки Arrangement не соседствуют, NEXT выполняет транспортный скачок. Это может вызвать слышимый разрыв, сброс эффектов или фазовые проблемы; в UI и документации нужно предупреждение.

# 4. МОДЕЛЬ СЕКЦИЙ

Внутреннее хранение позиции — музыкальные доли (beats), не секунды и не пиксели.

Пример структуры:

```json
{
  "schemaVersion": 1,
  "projectId": "flow-project-001",
  "title": "LIVE SESSION",
  "timeSignatureAssumption": "Live song signature",
  "sections": [
    {
      "id": "s-intro",
      "name": "INTRO",
      "startBeat": 0,
      "lengthBeats": 64,
      "digitone": {"enabled": true, "pattern": "A01", "programNumber": 0},
      "holdEligible": true,
      "defaultHoldBeats": 16,
      "notes": "atmosphere"
    },
    {
      "id": "s-groove",
      "name": "GROOVE",
      "startBeat": 64,
      "lengthBeats": 128,
      "digitone": {"enabled": true, "pattern": "A02", "programNumber": 1},
      "holdEligible": true,
      "defaultHoldBeats": 32,
      "notes": "main rhythm"
    }
  ],
  "performanceOrder": ["s-intro", "s-groove"],
  "preferences": {
    "quantizationBeats": 4,
    "digitoneControlEnabled": false,
    "stopMode": "confirm",
    "externalLoopConflictPolicy": "warn-and-disarm"
  }
}
```

`startBeat` и `lengthBeats` должны быть валидными положительными числами, начало >= 0, длина > 0. Пересекающиеся source-секции могут поддерживаться как преднамеренные «регионы», но в MVP по умолчанию запрещать их или помечать конфликтом. При изменении размера такта не переписывать сохранённые абсолютные beat-позиции без подтверждения. Отдельно указать, поддерживается ли смена размера такта внутри Live Set; в первой версии допустимо запретить сложные смены с явным сообщением.

Для Digitone: A01–H16 соответствуют MIDI Program Change 0–127, где индекс `(bankIndex*16)+(patternIndex-1)`. Не перепутать нулевую нумерацию MIDI с человекочитаемой.

# 5. СОСТОЯНИЯ ДВИЖКА

Не смешивать визуальное состояние кнопки и действительное состояние Live.

Минимальная state machine:

- `UNINITIALIZED` — ожидание `live.thisdevice`/готовности Live API.
- `IDLE` — устройство подключено, транспорт Live остановлен.
- `PLAYING` — Live воспроизводит Arrangement линейно.
- `HOLD_ARMED` — команда принята, ожидает безопасной границы.
- `HOLD_ACTIVE` — подтверждено, что Arrangement Loop имеет нужные значения и активен.
- `RELEASE_ARMED` — запланировано отключение loop или выход на границе.
- `JUMP_ARMED` — следующий переход ожидает границы.
- `JUMPING` — выполняется и проверяется переход.
- `ERROR` — обнаружен небезопасный конфликт/несогласованность; FLOW не отправляет неуверенные команды.

Состояния не должны зависать: определять timeout для завершения операции, реакцию на остановку транспорта, внешнее изменение Loop, смену Live Set, исчезновение секции и закрытие устройства.

Приоритет операций: STOP (если подтверждено) > отмена pending > RELEASE > JUMP > HOLD; конкретную политику явно зафиксировать и протестировать. Не отправлять два взаимоисключающих действия при одновременном нажатии. Повторные нажатия обезвреживать debounce (например, 100–200 мс на кнопку — подобрать по тестам).

# 6. HOLD: ДЕТАЛЬНАЯ СЕМАНТИКА

HOLD — не стоп транспорта. Это бесконечное циклическое воспроизведение заданной области Ableton Arrangement с продолжающимся MIDI Clock.

Моды области:

- `SECTION`: `[section.startBeat, section.startBeat+section.lengthBeats)`.
- `LAST 1 / 2 / 4 / 8 BARS`: текущая выбранная/подготовленная музыкальная область, границы которой выровнены по тактам. В MVP рекомендуется режим `SECTION` и фиксированные последние N тактов секции, а не непредсказуемый «захват прошлого».
- `CUSTOM`: пользователь задаёт startBeat + lengthBeats в ARRANGE, не во время сцены.

HOLD, нажатый внутри секции, должен подготовить петлю безопасным способом; при необходимости создать/активировать loop в конце соответствующего целого такта или секции. **Нельзя просто ждать конца петли и лишь тогда включать loop**, если Live уже прошёл точку wrap. Если выбранная область начинается раньше текущей позиции, следует проверить, позволяет ли установка Arrangement Loop заранее корректно повторить область без неожиданного прыжка. Любая неопределённость → «armed» и явная диагностика; не изображать успех до подтверждения API.

При активации сохранить снимок ранее действовавших `loop`, `loop_start`, `loop_length` Live. При выходе восстановить предыдущий loop только если это не изменит сценический поток неожиданно; иначе штатно оставить loop off и дать настройку `restore previous loop after stop` для студийного режима.

HOLD не должен отключать текущие аудиодорожки, приглушать Digitone, обнулять транспорт или переписывать Arrangement.

# 7. RELEASE: ПРИНЦИПИАЛЬНО ВАЖНЫЙ АЛГОРИТМ

Ожидаемое поведение: при удержании секции кнопка RELEASE заставляет закончить текущий оборот и затем продолжить линейную аранжировку с точки ПОСЛЕ петли, без лишнего повторения.

Нельзя считать, что установка `Song.loop=0` в момент границы автоматически будет безошибочной. JS LiveAPI работает не в realtime high-priority и может сработать с опозданием.

Требуемая стратегия:

1. Получить текущие loop start/length и фазу воспроизведения из наблюдаемого Live.
2. Считать RELEASE запросом на «конец текущего цикла» с минимальным safe lead time.
3. Использовать проверенный алгоритм предварительного disarm loop до границы, позволяющий линейно пройти через конец участка; если переключение позднее допустимого порога — назначить следующий цикл и показать `EXIT NEXT CYCLE`.
4. Альтернативный подход — на границе переносить позицию на loop end и выключать loop; допустим только если подтверждены отсутствие слышимых разрывов и сохранение MIDI-синхронизации в тестовом Live Set.
5. Если гарантировать безошибочную границу через Live API нельзя — честно документировать и измерить джиттер, предложить более стабильную native Live реализацию (например, штатное клип/локаторное управление) и не включать ненадёжную функцию в live-ready релиз.

Сделать тесты на BPM 80, 120, 160, циклах 1/4/8/16 тактов и повторных нажатиях рядом с boundary.

# 8. NEXT / PREVIOUS

Два строго разделённых режима:

- `SOURCE NEXT`: следующая по координате секция Arrangement.
- `SETLIST NEXT`: следующая запись `performanceOrder`, включая повторение той же source-секции.

Команда NEXT по умолчанию квантуется к следующему началу такта или заранее определённому концу секции. При работе HOLD NEXT должен либо запланировать завершение петли и переход на целевой startBeat, либо отказаться с пояснением, если подходящий безопасный переход не доказан.

Нельзя слепо вызывать `jump_to_next_cue` и надеяться, что он совпадает с кастомным setlist. Реальные точки перехода задаёт собственная модель секций. Для произвольного перехода допустимо устанавливать `current_song_time` при условии подтверждения API; обязательно тестировать слышимые последствия, расхождение эффектов и синхронизацию устройств.

Если текущий Live Set в Session View запустил клипы, которые переопределяют Arrangement, FLOW должен предупредить `BACK TO ARRANGEMENT` и не делать вид, что контролирует звучащие дорожки.

PREVIOUS: переход на начало текущей или предыдущей секции должен иметь фиксированную семантику, явно написанную в пользовательском руководстве (предпочтение: previous в setlist, независимо от абсолютного положения).

# 9. STOP / PAUSE

Различать:
- `HOLD`: продолжать звук, остановить развитие формы посредством петли.
- `PAUSE STRUCTURE`: заморозить автоматический переход по setlist, но не останавливать транспорт; доступно только если работает заранее заданная петля.
- `GLOBAL STOP`: выполнить остановку Live transport через Song API. Так как USB MIDI Transport Receive у Digitone может быть включён, Digitone тоже остановится.

По умолчанию `GLOBAL STOP` требует удержания кнопки или двойного подтверждения и визуально отличается от HOLD. На MIDI-контроллере предусмотреть отдельную безопасную MIDI-комбинацию или долгий press, насколько это позволяет конкретный контроллер и M4L-парсер.

# 10. DIGITONE II / USB MIDI

Поддерживаемые варианты:
1. USB MIDI для clock, transport и Program Change; звук по аналоговым выходам.
2. USB MIDI для управления, звук по другому выбранному пользователем пути.
3. Полностью без Digitone: FLOW управляет только Live и не показывает аппаратное соединение как ошибку.

Ableton — единственный master clock. Избегать MIDI loops (`Sync Out` в Live, `Clock Receive` на Digitone; обратный clock send обычно OFF).

Проверить параметры Digitone в его MIDI CONFIG:
- CLOCK RECEIVE = ON;
- TRANSPORT RECEIVE = ON (если желателен совместный play/stop);
- PRG CH RECEIVE = ON;
- INPUT FROM = USB либо MIDI+USB;
- корректный PROGRAM CHANGE receive channel в CHANNELS;
- корректный режим USB MIDI.

Управление Program Change архитектурно выделить в `DigitoneAdapter`, который может быть выключен. При включении он получает команды вида `requestPattern(A03, targetBoundaryBeat)`.

Выделенная MIDI-дорожка Live (`FLOW → DIGITONE`) с MIDI Effect и ручным выбором **MIDI To** Digitone II / нужный канал. Не предполагать, что Max Live API может сам менять глобальные MIDI Preferences, драйверы или устройства.

Реализовать отправку корректного Program Change по стандартному MIDI пути Max (проверить `pgmout`/`midiformat` в действующей версии Max, а не писать неподдерживаемое сообщение в `noteout`). Отправка на выбранном канале, номера 0–127 на уровне протокола.

**Требуемая проверка на железе:** MIDI PC может быть поставлен Digitone в очередь до конца текущего паттерна, согласно его pattern change/CH.LEN конфигурации. Отправка в момент старта целевой секции НЕ гарантирует старт нового паттерна в тот же такт. Разработать и испытать pre-send lead time / состояние pending pattern. Нужен конфиг `Change latency / boundary offset`, тест при длинах паттернов 16/32/64 steps и отличающихся master/track lengths. Если конкретная аппаратная конфигурация не допускает детерминированного переключения, отключить автоматический PC и предоставить ручной совет/режим.

FLOW не читает автоматически актуальный активный паттерн из Digitone, если это не подтверждено через входящие сообщения. UI показывает `REQUESTED A03`, не `CURRENT A03`, когда подтверждения от устройства нет. Предусмотреть ручной resync.

На seek/loop wrap не отправлять PC без политики. В настройках:
- `onSectionEntry`: отправить при входе в секцию;
- `onLoopWrap`: none (default) / resend requested pattern, по результатам тестов;
- `onManualDigitoneChange`: FLOW не подавляет ручное изменение, пока не наступила следующая команда;
- при STOP не отправлять All Notes Off без явного согласования, чтобы не испортить живое исполнение.

# 11. MIDI-КОНТРОЛЛЕР

Поддержать любой стандартный контроллер, который отправляет Note On/Off или CC.

Назначения по умолчанию (настраиваемые, не фиксированные):
- HOLD — toggle / arm;
- RELEASE — запрос выхода;
- NEXT — следующий блок setlist;
- PREVIOUS — предыдущий блок;
- LOOP LENGTH — шаг между 1/2/4/8/SECTION;
- STOP — подтверждаемая глобальная остановка;
- CANCEL — отменить pending action.

Два способа подключения:
A. MIDI Map Live для exposed параметров M4L (`live.text` / `live.toggle` / параметры device), проверив доступность mapping;
B. Явная MIDI Input дорожки устройства и MIDI Learn в M4L для Note/CC (при этом не пытаться читать все физические MIDI-порты непосредственно через LiveAPI).

В первом релизе предпочесть Live MIDI Map как надёжную базу; MIDI Learn — только если можно корректно обрабатывать входящие события на выделенной дорожке, не конфликтуя с другими инструментами.

Индикация: PENDING, HOLD ACTIVE, NEXT TARGET, ERROR. MIDI-feedback на LED — optional и строго по конкретной модели контроллера.

# 12. РЕДАКТОР ARRANGE — ДИЗАЙН

Отдельный эстетический мир FLOW. НЕ копировать NØIZ, KØRE, физические ручки Elektron или интерфейс Ableton. Строгий сухой цифровой минимализм, типографика и сетка; отсутствие объёмного «железа», теней, глянца, светящихся эффектов и бессмысленных анимаций.

Предлагаемая палитра, не догма:
- background: #0C0E10;
- raised panel: #131619;
- grid: #273037;
- text primary: #D9E0DF;
- text muted: #7D8A8C;
- active: #B8E28A (только у смысловых активных элементов);
- warning: #D88C77.

Шрифты: моноширинный системный / JetBrains Mono, с fallback, без распространения внешних файлов шрифтов. Высокий контраст, читаемость на ноутбуке и с расстояния. Широкое окно 1000–1300 px, плотный, но не мелкий текст. Должно работать при HiDPI и с изменением размеров окна.

Пример концептуальной иерархии (не буквальная вёрстка):

```text
FLOW / ARRANGE                              LIVE: 124.0  4/4
────────────────────────────────────────────────────────────
SOURCE | SETLIST                           ZOOM  −  +

      001       017       033       049       065
       │         │         │         │         │
       ┌─────────┬───────────────────┬─────────┐
       │ INTRO   │ GROOVE            │ BREAK   │
       │ A01     │ A02               │ A03     │
       └─────────┴───────────────────┴─────────┘

SECTION: GROOVE
START 017.1.1   LENGTH 32 BARS   PATTERN A02   HOLD YES

[+ SECTION] [DUPLICATE] [DELETE] [IMPORT LOCATORS] [SAVE]
```

Обязательные UI-операции:
- добавить/переименовать/удалить/дублировать секцию;
- выбор секции кликом;
- изменять длину и границы с snap по тактам в SOURCE, при условии что это только метаданные FLOW;
- перемещать порядок setlist drag-and-drop (не исходные клипы);
- показать вертикальный playhead по текущей позиции;
- показать CURRENT / NEXT;
- автоцентрировать при проигрывании (можно выключить);
- управление зумом, прокруткой;
- undo/redo локальных операций с документированной областью действия;
- валидация пересечений, пустых названий, отсутствующих ссылок, неверной длительности;
- ручной import cue points / locators Live, если доступен и работает через LOM;
- НЕ редактировать и НЕ создавать локаторы автоматически без разрешения.

`Import Locators`: считывать `Song.cue_points` и CuePoint.name/time, строить предварительный список диапазонов между соседними локаторами. Последняя секция требует явной границы (например, конец вручную), а не произвольной догадки. Показывать preview, затем пользователь подтверждает импорт. Не использовать cue points как единственный источник истины.

# 13. РЕЖИМ PERFORM — ДИЗАЙН

Крупные статусы с минимальным количеством строк, приоритет безопасности:

```text
FLOW / PERFORM                        ● LIVE SYNC

                FRACTAL POINT

                    GROOVE
                 BAR 048 / 064

NEXT                 BREAK
PATTERN REQUESTED     A03

[ HOLD ]        [ RELEASE ]
[ PREV ]        [ NEXT    ]

LOOP      SECTION     STATUS      PLAYING
──────────────────────────────────────────
SET 03 / 09                               34%
```

Состояние HOLD ACTIVE визуально отличается от HOLD ARMED. Не использовать зелёный цвет только ради украшения. SHOW `USB MIDI: ROUTED / NOT ROUTED / NOT VERIFIED`, а не неподтверждённый CONNECTED.

Встроенная компактная панель M4L: крупные элементы HOLD/RELEASE/NEXT, CURRENT, NEXT, индикатор ошибок, кнопка OPEN EDITOR. Не пытаться разместить полноценный горизонтальный таймлайн в узкой панели устройства.

Отдельный редактор — патчер/окно Max, управляемое из `.amxd`, с общим состоянием. Это всё ещё один M4L инструмент, не веб-сервер, не отдельный Electron app.

# 14. ПРЕДПОЧТИТЕЛЬНЫЙ СТЕК

- Max for Live MIDI Effect (`.amxd`), полноценный Max patch.
- `live.thisdevice` — сигнал готовности.
- `live.path`, `live.object`, `live.observer` и при необходимости JS `LiveAPI` для чтения/управления LOM.
- `jsui`/`mgraphics` для статичного и интерактивного таймлайна, либо стандартные Max UI элементы в MVP. Не использовать тяжелый web UI без причины.
- Max `dict`/`pattrstorage`/`autopattr` или совместимый надёжный механизм сохранения проекта в Live Set, плюс JSON экспорт и импорт.
- Транспортная логика на Max objects и проверенном beat-aware scheduler, не на догадках о тайминге JS callback.
- Включить `deferlow` там, где это требуется для LiveAPI; никогда не вызывать LiveAPI в high-priority scheduler.
- Поддержка Max Console для debug; единый фильтруемый лог без спама.

# 15. ПОДТВЕРЖДЁННЫЕ ВОЗМОЖНОСТИ LIVE API

Live Object Model, объект `Song` (`live_set`):
- `current_song_time`: позиция в beats, get/set/observe;
- `is_playing`: get/set/observe;
- `loop`: get/set/observe;
- `loop_start`: get/set/observe, beats;
- `loop_length`: get/set/observe, beats;
- `tempo`: get/set/observe;
- `signature_numerator`, `signature_denominator`: get/set/observe;
- `cue_points`: child list get/observe;
- `jump_to_next_cue`, `jump_to_prev_cue`, `jump_by`, `start_playing`, `stop_playing`.

Объект CuePoint: уточнить поля name/time и действия непосредственно по актуальной LOM-странице перед реализацией.

# 16. ПРИВЯЗКА К LIVE SET / СОХРАНЕНИЕ

При открытии существующего Live Set FLOW должен восстановить собственные данные, секции, порядок setlist, настройки контроллера и Digitone. Никаких внезапных изменений транспорта на загрузке.

Требования:
- структура сохранена в `.als` через совместимый механизм хранения M4L;
- альтернативный экспорт/импорт JSON с schemaVersion;
- безопасный migration при расширении схемы;
- авто-сохранение изменений в состоянии M4L без самопроизвольного перезаписывания внешних файлов;
- отдельное предупреждение при неконсистентности секций после редактирования Live Arrangement;
- отсутствие глобальных синглтонов, из-за которых два экземпляра FLOW могут управлять транспортом одновременно.

Сценическая политика: ровно один активный `TRANSPORT MASTER` экземпляр FLOW в Live Set. При обнаружении второго экземпляра второй должен работать read-only или требовать ручного назначения primary. Для MVP допускается явно запрещать несколько инстансов.

# 17. CONFLICT HANDLING И НАДЁЖНОСТЬ

Отслеживать:
- пользователь изменил Loop brace вне FLOW;
- пользователь запустил Session Clip, затронув Arrangement;
- транспорт остановлен во время HOLD_ARMED;
- Live Set закрыт или устройство перезагрузилось;
- invalid/missing section;
- изменились BPM или time signature;
- Digitone отсоединён;
- сменился/занят MIDI output;
- устройство оказалось в неподходящем треке или audio/MIDI routing сломан.

По умолчанию внешнее изменение loop во время активного FLOW должно переводить управление в safe state `MANUAL OVERRIDE`, а не бесконечно перезаписывать действия пользователя.

Нельзя внезапно включать global STOP из-за MIDI disconnect. Если Digitone отключается — Ableton и FLOW продолжают playback; показывать лишь warning.

Проверить поведение automation в Arrangement при скачках, retrigger audio clips, tails reverb/delay, задержки MIDI Clock и аппаратного фазирования. Описать реальные ограничения и практическую подготовку аудиоматериала: loop-safe stems, transition tails, отсутствие критических длинных хвостов на точке скачка.

# 18. ОСНОВНЫЕ ПРОВЕРКИ / ACCEPTANCE CRITERIA

## Тесты без Digitone (обязательные)

T01. Устройство открывается в Ableton Live 12 как MIDI Effect, после закрытия и повторного открытия set данные не теряются.
T02. Добавить 5 секций, переименовать, изменить длину и порядок; шкала отображает правильные beats.
T03. Импортировать локаторы, корректно обработать последний без известного end.
T04. Воспроизвести Live Set с двумя аудиодорожками и одной MIDI-дорожкой; FLOW показывает текущую секцию.
T05. HOLD на подготовленном 8-тактовом участке: Live действительно повторяет этот участок, аудио и MIDI продолжают звучать.
T06. RELEASE: при 10 циклах подряд устройство выходит без лишнего оборота и без случайной остановки; фактические отклонения записать.
T07. NEXT при линейном воспроизведении: прыжок попадает в заданную секцию и сохраняет transport running.
T08. NEXT из HOLD: проверить заранее определённую политику; не допускаются двойной jump или вечная петля.
T09. PREVIOUS: позиция соответствует правилам setlist.
T10. Внешний MIDI-контроллер инициирует HOLD / NEXT без мыши.
T11. External loop edit: FLOW обнаруживает вмешательство и переходит в безопасный режим.
T12. Сохранение/загрузка: UI и модель данных воспроизводятся, транспорт при загрузке не запускается сам.
T13. При ошибочном JSON импорт выдаёт понятное сообщение и не уничтожает действующий набор секций.
T14. Два экземпляра: запрещены конфликтующие транспортные команды.
T15. Устройство работает без Digitone и без установленного Overbridge.

## Проверки с Digitone II (отдельный блок)

H01. USB MIDI clock синхронизирует темп.
H02. Start/Stop по настройкам Digitone реагирует на Live.
H03. PC=0 выбирает A01, PC=1 — A02, PC=127 — H16.
H04. Правильный MIDI channel, неиспользуемые каналы игнорируются.
H05. Последовательность A01→A02→A03 на равных паттернах с разными CH.LEN.
H06. Проверить переключение в HOLD и после RELEASE.
H07. Проверить NEXT с transport jump и MIDI-sync: нет незамеченного несоответствия паттернов.
H08. Отключить USB в середине сета: Ableton продолжает безопасно, FLOW отображает warning.
H09. При ручном изменении паттерна Digitone FLOW не выдаёт неподтверждённое `CURRENT`.

## Матрица временных режимов

BPM: 80 / 120 / 160.
Размер такта: 4/4 обязательно; 3/4 проверить, или явно запретить с warning.
Длины: 1 / 2 / 4 / 8 / 16 / 32 bars.
Моменты нажатия HOLD/RELEASE/NEXT: начало, середина и последние 100–250 мс перед границей (воспроизводимые прогоны).
Записывать measured vs expected beats, поведение audio, MIDI и состояние Live API. Не придумывать результаты тестов.

# 19. ПЕРФОРМАНС И ПОВЕДЕНИЕ UI

Не допускать тяжёлого redraw на каждый тик MIDI Clock. Использовать Observer на state и адаптивную частоту обновления UI, например 10–20 FPS для playhead; реальный транспорт при этом берётся из Live, а не вычисляется накоплением времени в UI. При отсутствии изменений статическая графика не перерисовывается.

Критические действия должны работать при закрытом внешнем окне редактора. Кнопки контроллера и engine не зависят от видимости UI.

Обеспечить read-only статус, когда нет доступа к LiveAPI, и информативные сообщения об ошибках вместо молчаливых нажатий.

# 22. ТЕХНИЧЕСКИЕ ПРИОРИТЕТЫ И КРИТЕРИИ ОТКАЗА

Порядок ценностей: надёжное воспроизведение > предсказуемое управление > безопасность > сохранность данных > читаемый UI > дополнительные возможности.

Если точно квантизованный выход из Arrangement Loop при помощи Live API невозможно сделать устойчиво в данной среде, не маскировать проблему: сделать надёжный HOLD с ручным RELEASE или режимом с обозначенными ограничениями, составить отчёт о причинах и предложить проверенную альтернативу.

Если неконтролируемое изменение `current_song_time` разрушает синхронизацию Digitone или слышимый аудиопереход, NEXT из произвольной секции должен иметь отдельный режим SAFE / EXPERIMENTAL и не входить в stage-ready режим без тестов.

Все не подтверждённые возможности помечать `EXPERIMENTAL`, `UNVERIFIED` или `UNSUPPORTED`; не писать «готово» на основании того, что кнопка нарисована.
