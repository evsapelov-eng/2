# FLOW — архитектура (черновик, ревизия M0)

Документ фиксирует решения, принятые до испытаний, и **условия**, при которых они меняются. Разделы, помеченные *(зависит от E-n)*, окончательно утвердятся только по логам M0.

## 1. Модули (целевое разделение, §14 ТЗ)

```text
FLOW.amxd (Max MIDI Effect, один экземпляр = TRANSPORT MASTER)
├─ device-ui.maxpat         компактная панель: HOLD/RELEASE/NEXT, CURRENT/NEXT, ошибки, OPEN EDITOR
├─ flow-engine.maxpat       связка: live.thisdevice → deferlow → js; MIDI pass-through
│   ├─ live-bridge.js        ЕДИНСТВЕННОЕ место с LiveAPI: observers → события, команды → set/call
│   ├─ action-state-machine.js  состояния §5 ТЗ, приоритеты, debounce, тайм-ауты (чистая логика)
│   ├─ transport-engine.js   выбор нативного механизма перехода + «взвод» с запасом (чистая логика)
│   ├─ section-store.js      секции, performanceOrder, JSON schemaVersion, валидация (чистая логика)
│   └─ digitone-adapter.js   Program Change (M4), отключаемый
├─ editor.maxpat + timeline-ui.js (jsui/mgraphics)  ARRANGE/PERFORM в отдельном окне
├─ controller-input.maxpat  live.text/live.toggle параметры для Live MIDI Map (M3)
└─ diagnostics             единый лог (как в spike: кольцевой буфер + save log)
```

Правило: «чистые» модули не знают про LiveAPI и Max. Они получают события (`pos`, `loop`, `playing`…) и возвращают команды (`set loop 0`, `cue jump 3`…). Так их можно тестировать в Node на симуляторе (`tests/sim/live-sim.js`), как уже сделано для spike.

## 2. Потоки и тайминг

- Весь JS работает в low-priority потоке Max (DOC). LiveAPI в high-priority запрещён (DOC).
- Колбэки observer'ов только записывают состояние. Решения и команды выполняет Task-тик (5 мс в spike; реальный период меряет E1).
- **Принцип точности**: FLOW не пытается попасть в границу такта JS-таймером. Точную границу всегда даёт сам Live:
  - wrap петли Arrangement (HOLD, RELEASE, прыжок назад);
  - квантованный `CuePoint.jump` (прыжок вперёд, если на цели стоит локатор) *(E8)*.
  
  JS только «взводит» механизм заранее, с запасом `safeLeadMs`, который берётся из E5/E6 с двукратным запасом.
- Позиция: последнее наблюдённое значение + экстраполяция по темпу. Источник (observer или опрос) выбирается по E1.

## 3. Владение Loop / транспортом

- FLOW владеет `loop`, `loop_start` и `loop_length` только в состояниях `HOLD_*`, `RELEASE_ARMED` и `JUMP_ARMED`. Перед захватом делается снимок, после выхода по умолчанию остаётся `loop=0`; опция «restore previous loop» предназначена для студии (§6 ТЗ).
- Любое изменение этих свойств, которое не совпадает с ожидаемым результатом собственной команды (окно подтверждения + сравнение значений), переводит FLOW в `MANUAL OVERRIDE`. FLOW не перезаписывает действия пользователя. *(Видимость внешних правок — E11.)*
- `back_to_arranger = 1` → предупреждение `BACK TO ARRANGEMENT`, NEXT/HOLD блокируются до решения пользователя (§8).
- STOP — только `stop_playing` с подтверждением; при загрузке Set транспорт не трогается (spike уже так делает; проверка — E13).

## 4. Алгоритмы (гипотезы M0)

**HOLD (секция `[S, E)`)**
1. Если playhead в `[S, E)` и до `E` осталось больше `safeLeadMs`: выставить брейс, `loop=1`, прочитать значения обратно → `HOLD_ACTIVE` только после совпадения значений и уведомления observer'а.
2. Если до `E` осталось меньше `safeLeadMs`: поведение зависит от E6. Если Live при позднем `loop=1` прыгает назад (`JUMPED_BACK`), это недопустимо: команда отклоняется с сообщением `TOO LATE`. Если `NO_JUMP`, тоже `TOO LATE`, а HOLD не изображается. Вариант по умолчанию — отказ с явной диагностикой, без «догадок».

**RELEASE (`HOLD_ACTIVE`)**
1. Осталось больше `safeLeadMs` до конца петли: сразу `loop=0` (Live сам пройдёт конец линейно) → `RELEASE_ARMED`; переход в `PLAYING` после того, как позиция прошла `E`.
2. Осталось меньше: показать `EXIT NEXT CYCLE`, дождаться wrap и сразу после него выставить `loop=0`.
3. Если wrap всё-таки случился после команды (E4 `EXTRA CYCLE`), это фиксируется в логе как отклонение, а не скрывается.

**NEXT / PREVIOUS (переход к `T` на границе `B`)**, по убыванию надёжности:
1. `T == B` (следующая секция примыкает): это RELEASE или простое ожидание; прыжка нет.
2. `T < B`: петля `[T, B)` + `loop=1` с запасом; после wrap — `loop=0` *(E9)*.
3. `T > B`, на `T` есть локатор: `CuePoint.jump` в последнем такте перед `B` *(E8; при квантизации 1 Bar)*.
4. Иначе `current_song_time`. Если E7 покажет мгновенный прыжок, это JS-таймер с джиттером, режим **EXPERIMENTAL**, не stage-ready (§22 ТЗ).

## 5. Сохранение (план M2)

Основное хранилище — `dict` + `pattr` (hidden parameter) внутри Live Set; плюс JSON export/import с `schemaVersion`. Подлежит проверке в M2 (T01, T12).

## 6. Несколько экземпляров (план M3)

Ровно один TRANSPORT MASTER. Механизм (общий `send`/`receive` с id экземпляра, `---` префиксы M4L локальны для устройства, поэтому нужен глобальный канал) проектируется в M3 и проверяется T14.
