# FLOW — архитектура (ревизия M1)

## 1. Модули

```text
dist/FLOW.amxd  (Max MIDI Effect; unfrozen, рядом dist/flow.js)
│
├─ FLOW.maxpat  (генерируется tools/build_flow.py)
│   live.thisdevice → deferlow → "init" → [js flow.js]
│   midiin → midiout                     (MIDI дорожки проходит насквозь)
│   live.text ×6 (HOLD…CANCEL)  → js     (параметры Live: MIDI Map)
│   live.menu ×6 (опции)        ↔ js     (скрытые параметры; источник истины — документ)
│   [pattr flowdoc] blob-параметр ↔ js   (хранение документа в Live Set)
│   savedialog / opendialog     → js     (JSON export/import, отчёт SELF-TEST)
│
└─ flow.js = склейка src/:
    sections.js   модель секций, валидация, JSON, миграция, импорт локаторов, undo   (чистая логика)
    engine.js     состояния и механизмы переходов                                     (чистая логика)
    selftest.js   измерения на компьютере пользователя + сценарий движка, отчёт       (чистая логика)
    main.js       мост к LiveAPI, Task-тик, UI, хранение, реестр экземпляров          (Max)
```

Чистые модули не знают о LiveAPI и Max: события на входе, список действий на выходе. Поэтому в Node они тестируются тем же кодом, что работает в Max (`tests/sim/live-sim.js` эмулирует LiveAPI, Task, File, Global).

## 2. Потоки и тайминг

- `js` в Max работает в low-priority потоке, задержка Task переменная (DOC). LiveAPI в high-priority запрещён (DOC).
- Колбэки observer'ов только записывают состояние. Все записи в Live делаются в Task-тике раз в 10 мс (`engine.tick()` → `execute()`).
- **Точные границы задаёт сам Live, а не JS-таймер:**

| Действие | Механизм | Точность |
|---|---|---|
| HOLD | `loop_start/length` + `loop=1` заранее | wrap петли — нативный |
| RELEASE | `loop=0` до конца круга, Live сам проходит границу | нативная; нужен запас `safeLeadMs` |
| Переход назад (NEXT/PREV/повтор сетлиста) | петля `[T, B)`: на `B` Live сам переходит в `T`, затем `loop=0` | нативный wrap |
| Переход вперёд к локатору | `CuePoint.jump()` в последнем окне квантизации перед `B` | квантуется Live (DOC; SELF-TEST S7 проверяет) |
| Переход вперёд без локатора | `current_song_time` за `seekLeadMs` до `B` | таймер JS, **EXPERIMENTAL**, в SAFE запрещён |
| Следующая секция примыкает | ничего не делается (`LINEAR`) | — |

- `safeLeadMs` по умолчанию 150 мс. После SELF-TEST он равен `max(80, 2 × минимальный стабильно «чистый» запас из S4)` и сохраняется в документе (`calibration`).

## 3. Состояния (spec §5)

`UNINITIALIZED → IDLE/PLAYING`; `HOLD_ARMED → HOLD_ACTIVE` (только после echo от Live: `loop=1` и совпавшие границы); `RELEASE_ARMED` (с флагом «ждать wrap» при опоздании); `JUMP_ARMED → JUMPING → PLAYING` (после подтверждённого приземления около цели); `MANUAL_OVERRIDE`; `ERROR`.

Тайм-ауты и выходы:
- запись в loop не подтверждена за 1500 мс → `ERROR`, команды больше не отправляются, выход по CANCEL;
- остановка транспорта → операция отменяется, петля, которой владеет FLOW, выключается (или восстанавливается — студийная опция) → `IDLE`;
- переход не случился до `B + max(1 доля, 400 мс)` → `JUMP MISSED`, линейное продолжение, `PLAYING`;
- внешнее изменение loop или прыжок playhead, пока FLOW владеет петлёй → `MANUAL_OVERRIDE`.

Приоритеты (зафиксировано тестами):
- STOP первым нажатием только взводится (CONFIRM). Вторым нажатием отменяет всё и останавливает, но только если транспорт играет.
- CANCEL отменяет текущее; во время прыжка — только пока его ещё можно отменить.
- RELEASE / HOLD-toggle.
- NEXT/PREV отклоняются, пока есть взведённая операция («press CANCEL to change»), — это исключает двойной прыжок.
- **Ручной HOLD отменяет автоматический (не ручной) переход сетлиста, если тот ещё не случился.**
- Debounce каждой кнопки — 150 мс.

## 4. Владение петлёй

FLOW владеет `loop*` только в HOLD_*, RELEASE_ARMED и при прыжке через петлю. Каждая своя запись регистрируется как «ожидаемое эхо». Любое другое изменение в этот период — это вмешательство пользователя (MANUAL OVERRIDE): FLOW не воюет с пользователем. Повторная запись уже установленного значения не отправляется, потому что Live на неё не присылает уведомления.

## 5. Сетлист

`performanceOrder` — ссылки на секции, повторы разрешены. Текущий индекс отслеживается так:
- после прыжка FLOW — индекс цели;
- при линейном входе в секцию — следующий индекс, если секция совпадает, иначе ближайшее вхождение вперёд по сетлисту.

Auto-follow (`SETLIST: FOLLOW`): за ~2,5 с до конца секции FLOW взводит переход к следующей записи. Если она примыкает линейно, ничего не делает. Если механизма нет (вперёд без локатора в SAFE), показывает предупреждение и играет линейно.

## 6. Хранение

Документ (секции, сетлист, настройки, калибровка) хранится в `pattr flowdoc` — скрытом blob-параметре, который сохраняется в `.als`. Формат: `FLOW1:` + `encodeURIComponent(JSON)` — один символ Max без пробелов и кавычек. Тот же приём (blob-pattr, URL-кодированный JSON с префиксом) используют опубликованные устройства LFO-lab/SIGNe и michalhorcic/looper-dash.

- Восстановленные данные проходят ту же валидацию, что импорт. Если документ битый, FLOW стартует пустым и ничего не перезаписывает до первой правки.
- Меню — скрытые параметры (не сохраняются). FLOW выставляет их из документа; значения, пришедшие в течение 1 с после init, игнорируются (шум загрузки).
- JSON export/import (`schemaVersion: 1`). Ошибочный файл не трогает текущие данные.

## 7. Несколько экземпляров

Реестр `Global("flow_transport_master")` с heartbeat. Первый экземпляр становится мастером, остальные работают в режиме READ-ONLY. `take_over` передаёт роль. Если heartbeat мастера устарел больше чем на 3 с, роль можно занять.

## 8. Чего архитектура сознательно не делает

- Не создаёт и не меняет локаторы, клипы, автоматизацию.
- Не запускает транспорт при загрузке. Запускает только SELF-TEST по двойному нажатию.
- Не обещает sample-accurate тайминг для того, что делает JS; точность обеспечивают только механизмы Live из таблицы раздела 2.
